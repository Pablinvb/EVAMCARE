# EVAMCARE production activation — release 0.10.0

The owner confirmed existing records are disposable fictional data; no historical import is required. Production is not replaced until a verified release has working cloud credentials and administrator provisioning. No paid disk is needed with PostgreSQL.

## Implemented provider decision

Keep **local Auth only** for this release. The existing four roles, sessions, activation, recovery, scanner, commercial catalogs and appointments now support PostgreSQL through DATABASE_URL. No Supabase Auth SDK/session is enabled concurrently. SQL tables created by startup in the private evamcare_local schema preserve the current column model and IDs. RLS is enabled and all privileges to PUBLIC, anon and authenticated are revoked. Clients use FastAPI only; backend credentials belong exclusively in Render secrets. Per-user access is enforced by FastAPI on every request. The database-owning backend connection bypasses RLS: the private-schema boundary is defense in depth, not a claim that local opaque tokens become Supabase JWTs.

The earlier migration under supabase/migrations targets a **future Supabase Auth** schema, evamcare. It is tested in isolated PostgreSQL with platform stubs, including ownership, evaluator assignment, notes, scoped photographs, expiry and revocation. It must not be presented as the active identity model for this local-Auth release. Do not run it in the active runtime schema or map local opaque tokens to auth.uid(). A later Auth migration requires explicit identity mapping.

## Minimum secure setup

1. In the prepared Supabase form create EVAMCARE on Free, using a private password stored in your password manager. Automatic exposure of tables is disabled and automatic RLS enabled. If Supabase rejects a third free project, stop and choose an approved dedicated project or authorize a paid plan; do not remove or repurpose ACTA PRO/FASTLEDGER.
2. Copy the **session pooler** PostgreSQL connection (IPv4-compatible) into Render Environment as DATABASE_URL, privately. Backend defaults to verify-full TLS with system roots; if a custom CA is required provide its public certificate as PGSSLROOTCERT. Do not use a transaction pooler for this release's startup/session operations. Never paste the URL or password into chat.
3. Set DERMASCAN_POSTGRES_SCHEMA=evamcare_local, DERMASCAN_POSTGRES_SSLMODE=verify-full and the existing GitHub Pages CORS origin. Retain partner/referral secrets. Set administrator bootstrap email/password privately; the bootstrap does not invent a credential. Remove bootstrap values only after login is verified. SMTP recovery requires the variables documented in SECURITY_DEPLOYMENT.md and actual mail delivery verification.
4. Optional photographs: configure SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY in Render only. The backend creates/checks the evamcare-photos bucket as private on the first consented upload. Photos are normalized to JPEG, limits validated, and stored under random IDs. The frontend now supports explicit attachment to an existing scan and sharing the photographs scope. Reads proxy through FastAPI, check scope/expiry/revocation every time, and use Cache-Control: no-store; no public or long-lived signed URLs are issued. Existing scanner capture still is not automatically retained. Storage service credentials bypass Storage RLS and therefore backend authorization remains mandatory. If metadata insertion fails after upload, an orphan object can remain; reconcile privately rather than deleting objects blindly.
5. With secure configuration ready, deploy an isolated free staging service from this verified branch, or verify via a controlled deployment before routing production. Apply no paid plan/disks. The reference config deploy/render-postgres.yaml preserves the current service name/URL and uses manual deploy. Startup applies idempotent table creation to its private schema, and /api/v1/health verifies actual DB connectivity and reports database=postgresql, authProvider=local, version=0.10.0. Database connectivity failure is sanitized, without printing credentials.
6. Verify bootstrap login, patient creation, authorized reevaluation, refresh persistence, scoped professional access, revocation and actual private upload/download. Only then publish the same frontend to Pages and activate the existing production Render service. Keep the previous Git commit for rollback. Do not claim cloud activation based only on CI.

## Tests executed vs external dependencies

GitHub Actions tests the complete existing API against PostgreSQL 17, including analysis/history, appointments/catalogs, account roles, sharing/revocation, dashboard/timeline and reconnect persistence. It executes the prepared Auth RLS migration and SQL assertions against isolated auth/storage platform stubs; this verifies PostgreSQL policy behavior but not live Supabase Auth or Storage HTTP. The SQLite suite covers password recovery/provisioning and private photo access with a mocked Storage transport. Docker and the static bundle are built in CI. Actual cloud DB/TLS, SMTP delivery and Storage HTTP still require credentials and explicit live validation.
